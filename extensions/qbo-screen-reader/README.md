# Test Data Lab screen reader

This local Chrome Manifest V3 companion supplies read-only **observed screen evidence** to the reproduction assistant. Version 0.2 connects automatically. It supports English purchase orders with item quantity lines and separately requested Billed or Received quantity columns. Received is never substituted for Billed. Two consecutive automatic QBO Canada Received observations have been saved successfully after the foreground correction; other layouts and a Billed-labelled column remain unverified.

## One-time installation or update

1. Open Chrome Extensions (chrome://extensions), enable Developer mode, and choose **Load unpacked**.
2. Select C:\Projects\qbo\extensions\qbo-screen-reader. For an existing installation, click **Reload** instead.
3. Allow the extension access to its listed QuickBooks sites when Chrome asks. Stay signed in to QuickBooks in the same Chrome profile.
4. Keep the Test Data Lab case page open. The companion reconnects to existing app pages after installation, update and browser startup. No toolbar ON click or manual tab selection is needed.

The ON badge means the site permissions are available, not that a company or quantity was verified. The companion briefly activates its own QuickBooks tab in the initiating app window only when an authorized case requests a screen check. QuickBooks may defer rendering the PO fields while its tab is hidden. It reuses that tab while it remains untouched, refreshes the PO for each observation, and checks the company before and after capture. After capture it returns to the previously selected tab only if the reader tab is still active, no user interaction occurred and no tab switch happened during cleanup. If interaction state cannot be verified after an early loading or injection failure, it leaves the current tab in place. An authorized screen check can briefly show the reader while the case is in the background; it then returns to the previous selection, not necessarily the case. If the tab was closed, navigated manually or used for manual input/button interaction, a later request opens a fresh one. Existing user tabs are never adopted, closed or overwritten. Browser/extension restart can leave an old reader tab open; it is not assumed safe to reuse after ownership state is lost.

The companion never signs in, saves, deletes, submits accounting forms, or clicks an arbitrary page control. Its only page interaction besides fixed Home/PO navigation is the documented Company ID shortcut and Escape to close that information dialog. Sign-in, unsupported layouts, missing Company ID, hidden columns, incomplete rows or a different company remain explicit unavailable results. Disable the extension or remove its site access in Chrome to stop automatic access.

## Access and protocol

- Permissions: scripting, session storage and exact hosts localhost:5173, qbo.intuit.com and app.sandbox.qbo.intuit.com. No activeTab, all-sites, cookie, history or debugger permission. Persistent host access allows the fixed reader to run without a toolbar gesture. The implementation does not use that access for QBO API requests or background accounting-data collection.
- A case-authorized server tool creates a random single-use capability tied to owner, actor, case, run, company, environment, PO and revision. The authenticated case page carries that capability, never its JWT, to the companion.
- Before any QBO tab creation or inspection, the companion redeems the capability at the fixed local endpoint using a credential-free request. It uses the server-returned target, not the page's proposed target. It validates the capability again before navigation and after capture. Stop, revoked company access, expired requests and server restart invalidate it.
- The broker accepts one receipt. The engine re-reads the PO and rejects changes during capture. Any later case write makes the evidence stale by revision. Each screen check navigates afresh even when the requested PO URL is unchanged.
- Captured data is limited to company/record identity, displayed line item/description/ordered quantity, requested Billed or Received label/value, location and capture time. No screenshots, full-page dumps, credentials or hidden app state are collected. It is stored with the existing case evidence and audit receipt.
- Client DOM evidence is an observation, not cryptographic proof of QBO accounting state. A compromised local browser/app is outside this trust boundary. The server validates scope and consistency, not the provenance of every browser pixel.
- The versioned app bridge is reattached only to local app tabs on extension install/startup. Replacing the bridge removes its previous listener; obsolete responses cannot race the new connection. Connection status does not read QBO or start cases.

## Development and acceptance

Reader adapters remain fixed code; do not accept model-supplied JavaScript, selectors or arbitrary URLs. New screens require their own reviewed reader and fixtures. Keep the model CLI isolated; do not enable its general shell/browser plugins.

Focused tests: backend/test/reproduction-screen.test.js, reproduction-screen-reader.test.js and reproduction-engine.test.js. The DOM fixture launches temporary headless Chrome with all page requests intercepted; the background lifecycle uses mocked Chrome APIs. Neither contacts QBO. Run deterministic checks through the required Luna route.

Live acceptance update (2026-10-06): version 0.1 was installed and enabled in the owner's existing Chrome profile, and the app confirmed connection. Direct browser inspection of an existing test PO showed ordered quantity 6, three linked transactions and a RECEIVED column with 3.5. The actual Company ID dialog title and text required reader corrections, now covered by fixtures. The initial automatic capture attempts failed before readiness was corrected. Version 0.2 automatic reconnection was observed after extension reload without an ON click or app-page refresh. The next read-only check opened reader tabs automatically but failed while the company dialog and PO fields were not ready. The corrected worker subsequently returned a saved automatic case observation: exact RECEIVED label and value 3.5. A distinct Billed measurement remains unavailable. The server now handles one bounded retry for cold-page readiness failures with fresh authorization, without requesting an ON click, app refresh or another user message. The original extra 1.5-hour discrepancy remains unverified; an unavailable Billed measurement stays separate from Received.

Chrome's [scripting permissions](https://developer.chrome.com/docs/extensions/reference/api/scripting) support exact host access instead of activeTab. [Session storage](https://developer.chrome.com/docs/extensions/reference/api/storage#storage_areas) is cleared on extension reload/update and browser restart; lost ownership therefore creates a fresh reader tab rather than reclaiming a potentially user-edited tab ID.

Foreground correction accepted in the tested live flow (2026-10-06): two consecutive checks refreshed the existing PO and each observed RECEIVED 3.5. The case saved the labelled receipt and showed 6 ordered / 3.5 Received. No ON clicks, manual tab selection or QBO record writes were needed. The original Billed discrepancy remains unverified.
