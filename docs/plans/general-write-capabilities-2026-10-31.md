# General write capability fixtures — Job I, 2026-10-31

Scope: offline code and fixtures only. No QBO calls, MongoDB writes, service control or commits. Backend source was prepared and verified in a temporary directory before publication to minimize live reloads.

- Payment.TotalAmt is cash received. Line is optional; invoice applications minus credits cannot exceed cash received or invoice balances. QuickBooks computes read-only UnappliedAmt. Later application updates the existing Payment; its cash/receivables posting stays unchanged. Negative totals, overapplication, foreign customer references and caps remain refused.
- Invoice and SalesReceipt can explicitly select multiple synced active Canadian sales TaxCode IDs by line. Each code needs complete simple effective-dated rates (or an explicitly non-taxable code). The published default and Nova Scotia transition remain enforced; the superseded default code stays unavailable. Tax amounts remain server computed.
- Deposit may include negative processor fee lines to active Expense or Other Expense accounts alongside full linked undeposited receipts. The net bank deposit must remain positive. Absolute cash-plus-fee exposure counts toward the existing amount caps. Tax overrides, account overrides on linked lines and double deposits remain refused. Fee deposits post on their own day while historical source receipts remain read-only prerequisites.
- Invoice, Payment, SalesReceipt and BillPayment voids require accountant-created targets, protected-date/amount/inventory checks and a fresh version. Linked deposits must be removed first; paid invoices must be unlinked first. The wire batch uses update plus optionsData:void. Responses must prove a newer version with zero amounts, quantities and tax; ambiguous responses keep the existing recovery barrier.

Void endpoints confirmed from Intuit documentation: [Invoice](https://developer.intuit.com/app/developer/qbo/docs/api/accounting/all-entities/invoice#void-an-invoice), [Payment](https://developer.intuit.com/app/developer/qbo/docs/api/accounting/all-entities/payment#void-a-payment), [BillPayment](https://developer.intuit.com/app/developer/qbo/docs/api/accounting/all-entities/billpayment#void-a-billpayment), [SalesReceipt API reference](https://developer.intuit.com/app/developer/qbo/docs/api/accounting/all-entities/salesreceipt#void-a-salesreceipt) and [Intuit SDK endpoint correction](https://github.com/intuit/QuickBooks-V3-PHP-SDK/issues/357). [Intuit batch guidance](https://github.com/IntuitDeveloper/SampleApp-Batch-Java/blob/main/docs/building-smarter-batch.md) specifies update with optionsData:void. A webhook void event is not API endpoint evidence. RefundReceipt, CreditMemo, Bill, VendorCredit, Purchase, PurchaseOrder, Estimate, Deposit, Transfer and JournalEntry voids remain disabled because their Accounting API void endpoint was not confirmed.

Proof: backend/test/general-write-capabilities.test.js covers each case and day-close postings, changed bank readback on deposited cash, residual void postings, exact response/replay identities, service preparation/execution and protected-period fee classification. Existing affected guard, service, inventory, settlement, recovery, close-gate and period tests are included in verification.

Limits: these are deterministic fixtures, not live company evidence. The existing production close gate can attribute tax only when one tax account is unambiguous; separate-agency tax accounts still require independently retained rate-to-account evidence. The fixture with two tax accounts proves the pure posting rule and rejects swapped routing; it does not establish that missing live attribution. No tax account is guessed or merged to clear a close.
