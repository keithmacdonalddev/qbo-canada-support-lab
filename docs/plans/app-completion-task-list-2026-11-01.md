## How one session coordinates subagents

The main session owns the whole outcome, the ready-work queue, dependencies and integration. It should not repeatedly re-investigate source that an assigned worker has already established, or become a passive waiter while independent authorized work is available.

- **Keep the active queue small.** Maintain one primary feature, at most one urgent repair investigation, and ready historical execution where resources/authority permit. Record task ID, named owner (or explicitly unassigned), next observable result, proof, owned files/resources, blocker and checkpoint in the existing handoff or task row. These are responsibilities, not a demand for three agents or three simultaneous QBO writers. If slots are limited, serialize reviews and conflicting work; keep the feature's independent implementation/design advancing.
- **Delegate independent deliverables.** Use a short self-contained brief instead of copying the whole chat: task IDs and full-goal context, relevant files/rules, allowed edits, explicit file ownership, concrete proof, actual company/environment authority and exclusions, and the next checkpoint. Tell every worker it is not alone in the checkout, to reread files before editing and preserve others' work. Relay the current Windows hidden Node REPL/child-process launch requirement before any commands. Check the actual role/tool/model availability; role-file presence is not proof of capability. Use existing project model policy and current owner overrides.
- **Prevent collisions.** One implementer owns each file or shared contract at a time. Reuse the same worker for related follow-ups; do not create duplicate investigations or uncontrolled nested teams. The lead coordinates shared-file edits and staging/commit windows. Builders retain the normal owned-change commit/push obligation on canonical main/upstream; reviewers stay read-only. Native browser and accounting mutations retain their existing leases, writer fences and target-specific authorization.
- **Use reviews for concrete risk.** Obtain the distinct implementation and safety reviews required by ACCEPTANCE_AND_REVIEW.md for sensitive changes. Give reviewers the current diff, relevant original failure and exact proof. Resolve actual findings; re-review changed sensitive parts. Do not repeatedly review unchanged code, expand into optional cleanup or invent per-task approval gates. Finish one usable slice and its necessary integration/recovery before expanding scope.
- **Keep checks proportionate and cheap.** Builders reproduce real failing inputs and diagnose; deterministic runners execute exact commands and return exit codes/concise failures (Claude test-runner; Codex directly, under the execution contract). Use focused checks while building, then the justified integration checks for shared risks. A broad suite is not automatically the release gate for every isolated change; required safety checks cannot be skipped. Keep raw successful logs and private data out of the parent context. The lead verifies the integrated current files, rendered desktop flow and authorized direct outcome before reporting delivery.
- **Watch completion rather than poll endlessly.** Use existing job completion notifications/watchers when available. While a worker, test or review runs, do independent authorized work; fetch its result once complete and act on it. Request a concise result: changed behavior/files, observed proof, check exits, commit state, remaining dependency and next step. Do not ask another worker to redo the same work without new evidence.
