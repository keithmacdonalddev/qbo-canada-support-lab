# Critical financial report evidence

Implementation scope, 2026-10-15: collect all seven critical financial reports through fixed read-only endpoints and distinguish availability from the four existing arithmetic assertions. No report download establishes bank reconciliation or a realistic business.

Report-source version 1 (five reports) and its evaluator output remain unchanged for immutable historical baselines, published authorities and period evidence. New report-source version 2 adds GeneralLedger and CashFlow. New capture, preparation, owner approval and completion use a fresh scoped v2 observation. An existing active authority remains in place and receives new operation-period observations; it is never forced through replacement publication after activity. Untouched new publication requires a current v2 opening observation. Old evidence stays explicitly five-report evidence.

The reader retains bounded raw responses, exact company/environment/connection, report names, periods, basis, CAD currency, timestamps and account-list completeness. Seven-report availability is a separate result from arithmetic agreement. Missing, failed, malformed, wrong-scope or unsupported layouts cannot be shown as complete. Empty reports require explicit zero-report markers for decisions that permit zero openings.

Use GeneralLedger, as named by the Intuit SDK and current Intuit Reports migration support response; the discovery catalog's GeneralLedgerDetail name needs a recorded discrepancy. Do not silently try alternate endpoints. Main API documentation served only its application-loading shell during this research, so Canadian connected-company behavior remains unverified. References: [Intuit report-name SDK](https://static.developer.intuit.com/sdkdocs/qbv3doc/ipp-v3-java-devkit-javadoc/com/intuit/ipp/services/ReportName.html), [Intuit Reports migration response](https://help.developer.intuit.com/s/question/0D5TR00001JQa1O0AT/quickbooks-reports-api-migration-using-the-testingmigration-seems-to-have-a-semantic-mismatch-in-the-profitandlossdetail-report-response-can-someone-help-), [Cash flow reference](https://developer.intuit.com/app/developer/qbo/docs/api/accounting/all-entities/cashflow).

Required non-live proof: immutable v1 baselines still validate; new v2 observations require all seven correctly scoped reports; missing P&L, ledger or cash flow stays incomplete despite passing arithmetic; fresh preparation/approval fails before writes if availability fails; existing authority advances only after current v2 completion evidence. Verify identity/date/basis/currency, explicit empty layouts, read-only budgets, error redaction and canceled or changed-access reads. Run deterministic checks through Luna and obtain independent implementation/safety review. No new live authorization or storage migration is granted.

## Retention and decision boundaries

Preserve the existing six-megabyte retained-source and baseline BSON budgets. The two new detailed report bodies may use a versioned gzip/canonical-JSON envelope with exact raw byte length and SHA-256 digest; decoding must reject noncanonical base64/JSON, unknown fields, checksum/length mismatch and bounded-decompression overflow. Keep full report contents, not truncated samples presented as complete. Old v1 sources remain plain JSON and byte-compatible. The existing operation bounds are 31 calendar days and 500 steps. Verify the largest admissible fixed-template period with independent detailed reports and retain headroom; oversized observations fail in preparation/approval before dispatch, and source collection still fails closed after external company changes. Never bypass a size failure by marking a report complete.

Approval collects report data outside Mongo transactions, then binds the exact scope/period/plan/source hash/freshness to the current policy, writer, authority and calendar revisions in the approval transaction. Exact already-approved retries return the original decision. A new calendar advance must re-evaluate source v2 from retained full bodies. Existing committed v1 completion repair keeps its original meaning and does not require republishing an active historical authority.

## Current implementation and limits

Source v2 stores all seven bodies returned by the provider. General-ledger and cash-flow bodies use lossless, checked gzip envelopes; report/account retention remains capped at six million bytes, each decoded report at six million and their combined decoded report bodies at twelve million. New v2 validation checks header types, supported column widths, data and section cell types and explicit truncation warning rows. Historical v1 evaluation is unchanged. Public Book checks use the same bounded reader with current report-only authority around every logical GET/page and cancellation on disconnect. Read-only report access grants neither record inspection nor execution. Empty reports remain labelled empty; only explicit, structurally supported zero markers can satisfy availability.

Approval stores its full private observation in the existing append-only BusinessCandidate collection under an explicit business-approval-reports payload kind. Ordinary operation candidates reject that structure. Its source and evidence hashes link both the observation audit and the approved-decision audit. Inspection and exact acknowledgement retry validate both links. A missing mutable pointer cannot relabel a marked approval as an earlier five-report decision. True earlier approvals remain unlabelled and preserve their original authority. The source is collected outside the transaction; current authority, policy, writer and calendar revisions fence retention and the new approval together. There is no new collection, index or live migration in this change.

The first dispatch also rechecks fresh v2 availability and the named accounting checks, including for historical unsent approvals. Existing possibly-sent partial work retains its established recovery path. New calendar advancement requires re-evaluated retained v2 sources; an already committed v1 calendar receipt repairs without recollecting or reinterpreting its old reports.

Known upstream limitation: Intuit acknowledged GL truncation and modernization issues in its [developer support thread](https://help.developer.intuit.com/s/feed/0D5TR00001KebGJ0AZ). Recognized truncation warning rows are rejected. No parser can prove that an upstream response silently omitted unmarked records solely from its shape; this unit does not claim that proof, ledger-movement reconciliation or bank reconciliation. Those need independent record-to-report assertions. Report availability and full local retention are distinct from an independently complete company ledger. Canadian Production responses remain unverified in this unit.
