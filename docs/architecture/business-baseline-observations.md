# Saved baseline report observations

Implemented 2026-10-06. This slice preserves dated report evidence associated with an exact immutable saved business-plan version. It does not approve a baseline, establish ownership of existing records, activate a business, or verify complete historical/current activity.

## Capture and retrieval

The authenticated company router exposes GET/POST /api/company/business-baseline and GET /api/company/business-baseline/:id. Scope and actor/owner identity come from current server context. Capture requires explicit company membership and the existing reports.validate, blueprint.manage, qbo_data.read, app_data.read, reports.read and blueprint.read permissions. Read-only viewers use the narrower baseline.read action. Neither action grants operation execution.

The original QBO report reader has a trusted constructor-only baseline purpose. It reads five accrual/CAD report sources and the bounded complete current account list through the existing scoped client. Requests have a three-minute observation budget, bounded retained bytes, cancellation, current authority checks and exact source hashes. Separate requests are not an atomic historical inventory. Missing/failed report checks remain visible; balanced reports do not prove realistic or complete records.

A capture selects opening-balances or company-survey. Opening balances must end on the day before the selected blueprint opens; a current survey cannot silently substitute for that date. Periods are elapsed, ordered and at most 366 days. The exact request, blueprint identity, original sources, observation interval, recalculated checks and hashes are retained in the append-only BusinessBaseline model. Public responses omit raw sources. Acceptance and activation stay false; ownership stays unverified. Original contract-1 observations have no inventory evidence. New contract-2 captures also retain a minimized current-record inventory, described below.

The observation and compact audit receipt commit together. Actor, owner, connection and active membership documents participate in transaction write conflicts via businessObservationVersion. Current authority and setup completion are checked before provider reads and within the save transaction. Sources must remain fresh at save. Retrieval recalculates the source checks and requires the matching audit receipt; historical observations retain their original timestamp rather than being relabelled current.

A deterministic request identity preserves the original observation after a lost acknowledgement. Changed input under the same request identifier is rejected. The Company panel stores the exact pending request in scoped session storage before sending and retains it for uncertain failures. Client date validation precedes persistence; only the explicit pre-provider BUSINESS_BASELINE_REQUEST_INVALID / HTTP 400 / notSaved:true response releases the request for correction. Other errors do not authorize a fresh capture. No browser-stored report sources or credentials are added.

## Explicit storage boundary

The baseline-observations setup profile is separate version 3. It prepares the two existing blueprint collections plus businessbaselines and its exact history index, with existing legacy prerequisites and explicit owner-membership/scope-counter/audit changes. The blueprint v1 and business-operations v2 definitions and approval scope remain unchanged. Their hashes and receipts do not authorize baseline storage.

Initial v3 setup requires businessbaselines to be empty database-wide. Capture requires a valid completed v3 setup receipt in addition to collection/index readiness. The receipt binds the exact target, reviewed definition and replica deployment. Creating the last index therefore cannot unlock a concurrent capture before setup finishes. Existing observations remain readable when capture readiness is unavailable. The runtime invokes only read-only receipt validation; no startup/route invokes setup application.

No live preparation was applied. The previously pending v2 setup approval does not include v3. Live application requires a separate concrete preview and explicit target-specific approval; this implementation is not that approval.

## Current supported-record inventory — 2026-10-06

New captures compose the report reader with business-record-inventory through the existing baseline service. Both sources share a three-minute caller deadline and cancellation; a failed source cannot save a report-only replacement. Each reader uses the exact current company/actor authority and original QBO client. No permission, setup definition, collection, index, or live preparation is changed by this integration.

The inventory covers the exact 19 entity types exposed by Records: Customer, Invoice, Payment, CreditMemo, Bill, BillPayment, VendorCredit, Vendor, Item, Account, JournalEntry, Estimate, Deposit, SalesReceipt, RefundReceipt, Purchase, PurchaseOrder, Transfer and TimeActivity. All dates are included. Customer, Vendor, Item and Account queries explicitly include inactive records. Pagination uses fixed 1,000-row pages and a short or empty final page. This respects Intuit's documented [query pagination limit](https://static.developer.intuit.com/output_html/qbo/docs/learn/limits-and-throttles.html).

The first complete pass finishes before the second begins. Each requires exact response/pagination fields, valid identities and SyncTokens, full records, unique IDs and matching declared totals when present. Exact per-entity identities, versions, current active/date values and canonical content hashes must agree across both passes. Scope and authority are checked before and after every page. A failed/unsupported query, changed record, omitted page, warning, duplicate or exhausted budget is an error, never an empty type or a complete observation.

Only record IDs, versions, content hashes and current Active/TxnDate values are retained in a private manifest. Names, contact details, transaction lines and amounts are not copied into that manifest. The public view shows exact type coverage, counts, active/inactive counts, transaction date ranges, scan interval and limitations. It does not expose the manifest. The report account list must have the same IDs and full-content hashes as the inventory account list.

The reader bounds each record at 1MB, page at 8MB, aggregate raw reads at 300MB, each compact pass at 25MB/100,000 records, and runs two workers per pass. The report reader runs concurrently, so the combined capture can have four source requests in flight. An already-dispatched SDK GET may finish after cancellation; late results cannot be saved or cause new page requests. Retained combined observations have a 14MB canonical JSON limit and an actual BSON size check below 15MiB, leaving schema overhead below MongoDB's 16MiB document ceiling. Larger observations fail before writes and require a future chunked storage workflow; this bounded implementation is not proof of support for arbitrarily large companies.

Contract 2 adds immutable inventorySources on BusinessBaseline, binds its summary/hash into payload evidence and its hash/version/interval into the compact audit, and revalidates both retained sources on inspect. The original contract-1 view and audit semantics remain readable without invented inventory. Lost acknowledgements reuse the original observation rather than running new scans. Source freshness and access are checked again inside the existing atomic save; no records are adopted and acceptance/activation remain false.

Two matching passes are evidence of observed stability, not an atomic QBO snapshot, historical contents, deleted-record history, business ownership or coverage of every QBO feature. Employee, tax, project and other types outside the named set remain separate evidence requirements. Even an opening-balances report capture inventories current records at capture time; the UI states this explicitly.

Verification: the original five focused suites passed 50 cases, then the three affected suites passed 38 after adding a production-service composition test with the actual report/inventory readers and simulated QBO transport (51 distinct focused cases overall). Four changed backend syntax checks, frontend build/lint and diff check passed; existing chunk-size/hook warnings remain. Both independent source reviews found no blocking findings. Desktop fixture interaction showed the full 19-type table, inactive counts, historical date span, empty types, legacy no-inventory state, focused result heading and lost-response retry recovery. These were isolated fixture calls, with no QBO or database writes. Real Canadian query shapes across all 19 types, live capture, Mongo persistence and independent rendered acceptance remain unverified.


## Captured-record review — 2026-10-06

Saved contract-2 inventories now support record-by-record review before any baseline membership/adoption decision. GET /api/company/business-baseline/:id/inventory accepts only a supported entity, bounded limit (1–50) and an opaque cursor tied to that exact baseline ID, evidence hash, inventory hash and entity. It validates the saved sources and original audit before returning selected IDs, saved SyncTokens and captured active/date values. The full manifest and content hashes remain private. Contract-1 observations return an explicit no-inventory error, never a fabricated empty list.

GET /api/company/business-baseline/:id/inventory/:entity/:recordId first requires the record to exist in that validated captured manifest. A fixed ID query through the original scoped QBO client uses the same full-query representation as capture; list types explicitly include inactive records. Exact response shape, record identity and version are checked. The response distinguishes matching content/version, a different version, a different exact content hash, and a valid query that returned no row. No empty or failed query is described as deletion, and a content difference does not identify an accounting change or its cause.

The internal baseline.review action requires qbo_data.read in addition to baseline.read permissions. It follows the existing legacy read-only bridge without granting capture, adoption or operation execution. Current actor/owner/company authority is checked before and after both the QBO query and creation-history lookup. The comparison has a one-minute caller deadline and cancellation; an already-dispatched SDK GET may finish later but its late result cannot be returned. The HTTP route propagates disconnect cancellation. QBO authentication errors stay upstream 502 responses, not app logout 401 responses.

Creation history uses the existing exact scoped origin reader. Failure or mismatched origin evidence is explicitly incomplete/unavailable and does not hide a successful record comparison. Historical creation receipts remain separate from current content and baseline membership. Public results include bounded saved/current identities, separate capture/read/check times, origin summaries and limitations; no full QBO record or content hash is exposed by these review endpoints. Inspection of full current fields remains on the existing Records page.

The Company observation detail has a captured-type selector, immutable inventory pagination, per-record current comparison, creation history and links into Records/support cases. Changing company, observation, record type or page discards prior comparisons; newer requests cancel older ones and returned identities are checked against the exact selected observation. Results receive focus. This is an evidence workflow, not a saved classification or adoption action.
