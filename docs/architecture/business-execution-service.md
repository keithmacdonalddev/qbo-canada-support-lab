# Durable business execution requests

The authenticated /api/business-operations routes expose saved approved operations. POST /:id/execute accepts only the exact planHash and a caller-generated requestKey (16–100 safe characters). It saves the scoped request and its audit in one transaction, then returns 202 before running provider work. The server resolves company, environment, owner and actor; body/query overrides cannot choose them. Read/list routes return bounded progress, exact server-resolved scope, current execution permissions and public execution state without lease tokens or private request identity. The [desktop operations panel](business-operations-desktop.md) uses these reads to gate controls.

The service uses the assembled business runtime, not a second execution engine. Existing approval, current membership, company writer, worker lease, request receipt, graph evidence and period completion checks remain authoritative. Construction/import does not start workers. Explicit backend startup starts a ten-second recovery scan; server close stops new launches without interrupting possibly-sent provider requests. Only saved pending requests are eligible. No operation, approval, collection, index, membership or business schedule is invented by recovery.

Recovery has at most three local workers. Runtime leases protect work across processes; a fresh worker waits for an active lease to expire. Scans rotate an operation-ID cursor, so damaged older requests cannot repeatedly starve later valid work. A damaged request remains pending for repair and produces a bounded worker diagnostic; it is not treated as completed or silently removed. The operation listing uses descending operation ID and an exclusive ID cursor, not chronological creation order.

Execution completion is reported only when the runtime returns complete and the saved run is verified. A failed transactional settlement retains the pending request for recovery, and completed records remain protected by existing transport receipts. Failed/unverified attempts retain their progress and require a new explicit request after the cause is addressed. The service does not automatically repeat unsuccessful experiments forever.

Stop records the actual stopping actor. Replacing a pending execution with a stop continuation also retains an audit of the superseded request. A queued, unstarted approved run can stop transactionally without touching QuickBooks. Active or previously blocked work first receives the calendar stop flag, then a durable stop continuation, even if the previous execution request already settled. That continuation reasserts stop before using the runner's recovery path; it cannot use Stop to resume ordinary creation. A competing completion can release calendar ownership, so terminal/committing states use completion repair/inspection without reasserting Stop against the released calendar.

The run schema adds executionRequest and an index on executionRequest.pending plus _id. Runtime readiness requires the declared collections/indexes already prepared and transaction-capable storage. Startup checks readiness; it never prepares storage. This new index is not covered by the earlier blueprint-only storage preview.

## Verification and remaining acceptance

Focused fixtures exercise the actual assembled runtime with a stubbed QuickBooks transport, transactional fixture stores, route authentication, enqueue/reuse, post-enqueue revocation, interrupted service recovery, failed settlement rollback, queued stop attribution, blocked-record stop recovery, completion/stop races, fair scanning and bounded company-scoped pages. These are not live MongoDB restart or real QuickBooks evidence.

The desktop controls are now integrated and inspected with fixtures; the operation preparation/approval application path and production storage preparation still need integration and acceptance. This background slice does not establish whole-app completion or a realistic company through the current business date.
